# DddPhotoRec — Photo Recovery Toolkit

Небольшое настольное приложение, которое помогает разобрать результат работы
программ для восстановления фото/видео. После восстановления с диска обычно
остаётся огромная папка «recovered», где много файлов, которые *уже есть* в вашей
упорядоченной библиотеке. Инструмент сравнивает восстановленные файлы с вашими
оригиналами и раскладывает их на две группы:

- **дубликаты** — восстановленные файлы, совпадающие с тем, что у вас уже есть
- **восстановленные** (уникальные) — файлы, которым нет пары среди оригиналов,
  то есть их действительно стоит сохранить

Сравнение идёт **по содержимому** (для фото — по пикселям), поэтому оно не зависит
от имён файлов, дат или структуры папок.

---

Приложение — это **набор инструментов**: настольный интерфейс с вкладками, где
живёт несколько утилит для работы с медиа. Кроме восстановления оно умеет
переименовывать и раскладывать библиотеку по дате съёмки, а также искать дубликаты.

## Как пользоваться каждой вкладкой (простое руководство)

В приложении три инструмента, по одному на вкладку. **Ничто здесь никогда не
удаляет ваши файлы** — в худшем случае это копия или переименование, которое можно
отменить. Внизу каждой вкладки есть **панель логов**, показывающая, что происходит
во время работы.

### 📸 Вкладка 1 — Photo Recovery (восстановление фото)

**Для чего.** После спасения фотографий со сломанного или отформатированного диска
(программой вроде PhotoRec) получается одна большая беспорядочная папка. Многие из
этих фото у вас *уже есть* в обычной библиотеке. Эта вкладка раскладывает
восстановленные фото на «уже есть» и «действительно новое».

**Вы выбираете три папки:**

- **ORIGINAL** — ваша существующая, аккуратная библиотека (то, что у вас уже есть).
- **RECOVERED** — беспорядочная папка, созданная программой восстановления.
- **OUTPUT** — пустая папка, куда запишется отсортированный результат.

**Шаги:**

1. Нажмите каждую кнопку *Select … folder* и выберите папку.
2. *(Необязательно)* включите **«Move files instead of copying»**, чтобы
   восстановленные файлы перемещались, а не копировались. Выключено (по умолчанию)
   — безопасно, только копирование.
3. Нажмите **Process files** и следите за логом.

**Что получится в OUTPUT:**

- `duplicates/…` — восстановленные фото, которые уже были в библиотеке.
- `recovered/…` — действительно новые фото, которые стоит сохранить.

**Полезно знать.** Фотографии сопоставляются по **самому изображению**, а не по
байтам файла, поэтому восстановленная копия совпадёт, даже если программа
восстановления добавила «хвост» или удалила данные о дате.

### 🗂️ Вкладка 2 — Photo & Video Renamer (переименование)

**Для чего.** Превращает беспорядочные имена вроде `IMG_1234.HEIC` в аккуратные
имена на основе даты и раскладывает файлы по папкам год/месяц — например
`2024/10/2024-10-05_14-30-22.heic`.

**Шаги:**

1. Нажмите **Select INPUT folder** — папка с фото/видео для наведения порядка.
2. Выберите **шаблон имени** из выпадающего списка или введите свой. Строка
   **Example** показывает, как именно будет назван файл.
3. Нажмите **Rename all**.
4. Не понравилось? Нажмите **Undo last rename**.

**Откуда берётся дата.** Из реальной даты съёмки фотографии (её метаданные), либо
из даты в имени файла, либо из даты самого файла — именно в таком порядке.

**Необязательное место в имени.** Если в шаблоне есть `{loc}`, к имени добавляется
город, где сделано фото (читается из GPS фотографии, **полностью офлайн**). Для
фото без GPS этот кусок просто пропускается.

**Полезно знать.** Файлы **перемещаются** в новые папки по дате внутри той же
папки. Undo возвращает их обратно (пока вы не закрыли приложение).

### 🔍 Вкладка 3 — Duplicates Finder (поиск дубликатов)

**Для чего.** Находит одинаковые фото/видео **внутри одной папки** (и её
подпапок) — одну и ту же картинку, сохранённую несколько раз. Ничего не удаляется;
что удалять — решаете вы.

**Шаги:**

1. Нажмите **Select INPUT folder**.
2. Нажмите **Scan for duplicates** — это только *смотрит*, ничего не меняет.
   В папку записывается отчёт `.md`, а группы дубликатов выводятся в лог.
3. Затем выберите одно действие:
   - **Move to DUP folder** *(рекомендуется)* — переносит лишние копии в папку
     `DUP/`, которая повторяет структуру ваших папок, чтобы их было удобно
     просмотреть, сравнить и удалить вместе.
   - **Rename in place** — добавляет префикс `DUP_` к лишним копиям, чтобы их было
     видно и можно было найти поиском.
4. **Undo** отменяет последнее действие.

**Какая копия остаётся?** **Самый старый** файл в каждой группе остаётся нетронутым;
помечаются или перемещаются более новые копии.

**Полезно знать.** Фотографии сравниваются по **самому изображению**, поэтому
точные копии находятся, даже если размеры файлов немного отличаются (из-за «хвоста»
или изменённых метаданных).

## Стек технологий

| Область         | Выбор                                                             |
| --------------- | ----------------------------------------------------------------- |
| Язык            | Python 3.10+                                                      |
| GUI             | [Flet](https://flet.dev) `0.28.3` (десктоп)                       |
| Хеширование     | `hashlib.sha256` (стандартная библиотека)                         |
| Метаданные фото | Pillow EXIF + `pillow-heif` (HEIC)                                |
| Геокодинг       | `reverse-geocode` (офлайн, на устройстве)                         |
| Выбор папки     | Tkinter `filedialog`, запускается как подпроцесс                  |
| Сборка          | Hatchling                                                         |
| Зависимости     | `flet[all]`, `jpegio`, `pillow`, `pillow-heif`, `reverse-geocode` |

> `pillow` / `pillow-heif` читают дату съёмки и GPS из фотографий;
> `reverse-geocode` превращает GPS в название места **офлайн** (координаты никогда
> не покидают компьютер). `jpegio` пока объявлен, но не используется.

## Инструмент восстановления (как он работает)

Пользователь выбирает три папки и нажимает **Process files**:

1. **ORIGINAL** — существующая упорядоченная библиотека (источник истины).
2. **RECOVERED** — беспорядочный вывод программы восстановления.
3. **OUTPUT** — куда записывается результат.

Прогон запускается методом `PhotoRecoveryService.run()`
(`features/recovery/service.py`):

### 1. Сканирование оригиналов

`MediaScanner` рекурсивно обходит папку ORIGINAL (`rglob("*")`) и оставляет только
файлы с поддерживаемыми расширениями:

- фото: `.jpg .jpeg .png .webp .heic`
- видео: `.mp4 .mov .m4v .avi .mkv .3gp`

### 2. Построение индекса (сигнатуры содержимого)

`OriginalIndex.build()` (асинхронно, с прогрессом и отменой) вычисляет **сигнатуру
содержимого** для каждого файла библиотеки и хранит `dict[сигнатура → путь]`:

- **Фото** → SHA-256 от **декодированных пикселей** (`image_signature`). Это
  игнорирует контейнер файла, «хвост»-заполнение и метаданные EXIF — поэтому фото и
  его восстановленная копия дают одинаковый хеш, даже когда их байты различаются.
  В этом суть: программы восстановления добавляют «хвост» и меняют EXIF, что
  меняет байты, но **не пиксели**.
- **Видео** → SHA-256 от **сырых байтов** (`HashCalculator`); пиксели дёшево не
  декодировать, поэтому видео сопоставляются точно по байтам.

Также запоминается набор встреченных размеров изображений — только для диагностики.

### 3. Сканирование и классификация восстановленных файлов

Для каждого файла из папки RECOVERED `DuplicateFinder.find_original()` вычисляет ту
же сигнатуру содержимого (пиксели для фото, байты для видео) и ищет её в индексе.
Совпадение → **дубликат** (найденный файл библиотеки); нет совпадения →
**восстановленный**. Промахи разделяются в логе: восстановленное фото, у которого
размеры совпадают с фото из библиотеки, но пиксели отличаются, помечается как
вероятная **пересжатая/отредактированная** версия, а не как действительно новое
(чтобы ловить такие, нужно нечёткое/перцептивное сравнение).

### 4. Раскладка результата

`DuplicateProcessor` записывает каждый файл в OUTPUT:

- **Дубликаты** → `OUTPUT/duplicates/<относительный-путь-оригинала>/<имя>_DUP.<ext>`
  — повторяет расположение оригинала в библиотеке, чтобы было видно, какому файлу
  соответствует восстановленная копия.
- **Уникальные** → `OUTPUT/recovered/<имя-папки-recovered>/<относительный-путь>`
  — сохраняет структуру самой папки recovered.

По умолчанию файлы **копируются** (`shutil.copy2`); при `move_files=True` —
перемещаются (`shutil.move`).

### 5. Прогресс и отмена

Сервис сообщает о прогрессе через колбэк `log` (связан с панелью логов) и часто
проверяет колбэк `cancel_check`, поэтому прогон можно остановить на полпути. Цикл
периодически отдаёт управление событийному циклу (`asyncio.sleep(0)`), чтобы
интерфейс Flet оставался отзывчивым.

## Renamer (вкладка Photo & Video Renamer)

Переименовывает медиа по **дате съёмки** и раскладывает по подпапкам с датой
(`2024/10/…`), превращая `IMG_1234.HEIC` в, например,
`2024/10/2024-10-05_14-30-22.heic`. Поток намеренно минимален: выбрать одну
**входную папку**, выбрать шаблон, нажать **Rename all**. Файлы **перемещаются на
месте** внутри этой папки, а кнопка **Undo** отменяет весь прогон.

### Откуда берётся дата

`DateResolver` пробует источники по порядку и запоминает, какой сработал:

1. **EXIF** `DateTimeOriginal` — реальное время съёмки (фото; HEIC через
   `pillow-heif`). Читает `ExifReader`.
2. **Имя файла** — даты в именах вроде `IMG_20241005_143022`, `PXL_…`, WhatsApp
   `IMG-20241005-WA0001` (только дата → полночь).
3. **Файловая система** — `st_birthtime` / `st_mtime`, всегда доступно как крайний
   вариант. **Видео** используют этот путь (библиотеки метаданных видео в v1 нет).

### Шаблон имени

Интерфейс предлагает **выпадающий список пресетов**, редактируемое **поле шаблона**
и **живой предпросмотр**. Шаблон — это смесь обычного текста, токенов даты и `/`
(создаёт подпапки). `NameBuilder` подставляет токены, форматирует дату, вставляет
дополнения, очищает каждый элемент пути (запрещённые символы, слишком длинные имена)
и приводит расширение к нижнему регистру.

| Токен                 | Значение                     |     | Токен       | Значение                            |
| --------------------- | ---------------------------- | --- | ----------- | ----------------------------------- |
| `YYYY` / `YY`         | год                          |     | `HH` / `hh` | час 24ч / 12ч                       |
| `MM` / `MMM` / `MMMM` | месяц числом / Oct / October |     | `mm` `ss`   | минута, секунда                     |
| `DD`                  | день                         |     | `{name}`    | исходное имя файла (без расширения) |
| `/`                   | разделитель подпапок         |     | `{loc}`     | название места (см. ниже)           |

Шаблон по умолчанию: `YYYY/MM/YYYY-MM-DD_HH-mm-ss`. Если два файла дают одно имя,
добавляется `_1`, `_2`…

### Место (`{loc}`)

Вычисляется только если шаблон содержит `{loc}`. `Geocoder` читает GPS из EXIF и
определяет ближайший город через `reverse-geocode` — встроенный набор данных,
**полностью офлайн**, координаты не покидают компьютер. Файлы без GPS просто
пропускают этот кусок, и имя остаётся корректным.

### Применение и отмена

`RenamerService.run()` сканирует, определяет дату каждого файла, вычисляет путь
назначения и перемещает файл (`shutil.move`), пропуская файлы, уже стоящие на
месте, ведёт лог прогресса и учитывает Cancel (тот же асинхронный подход, что и в
восстановлении). Возвращает список перемещений `RenameOperation(source, target)`.
`undo_operations()` проигрывает их в обратном порядке (`target → source`) и удаляет
опустевшие папки. Undo **действует в рамках сессии**: отменяет самый последний
прогон, пока вы не запустите новое переименование или не закроете приложение.

### Ключевые компоненты

| Компонент         | Ответственность                                        |
| ----------------- | ------------------------------------------------------ |
| `DateResolver`    | Дата съёмки: EXIF → имя файла → файловая система.      |
| `ExifReader`      | Pillow / pillow-heif: `DateTimeOriginal` и GPS.        |
| `Geocoder`        | Офлайн GPS → название места, с кешем в рамках прогона. |

## Duplicates Finder (поиск дубликатов)

Находит дубликаты файлов в пределах одной входной папки и помечает лишние копии —
и никогда ничего не удаляет, так что финальное решение за вами. Намеренно в два
шага:

1. **Scan** (только чтение) → находит группы дубликатов, наполняет лог и пишет
   отчёт в Markdown. Ничего не трогает.
2. Проверьте результат и выберите одно из двух явных действий:
   - **Move to DUP folder** (рекомендуется) → переносит каждый дубликат в
     `DUP/<тот же относительный путь>`, чтобы все копии собрались в одном удобном
     для просмотра дереве, повторяющем исходную структуру (оставленный файл лежит
     по такому же пути вне `DUP/`). Папка `DUP/` пропускается при будущих
     сканированиях, поэтому действие идемпотентно.
   - **Rename in place** → добавляет префикс `DUP_` к каждому дубликату.
3. **Undo** отменяет последнее действие (общий `undo_operations`, работает для
   обоих вариантов).

### Как определяются совпадения

`DuplicateScanner.scan()` разделяет файлы по типу и использует ту же логику по
содержимому, что и вкладка восстановления, поэтому копии, отличающиеся только
«хвостом» или EXIF, всё равно группируются:

- **Фото → по декодированным пикселям.** Сначала дешёвый проход по **размерам**
  (`read_dimensions`, без декодирования) отбирает кандидатов; декодируются и
  **хешируются по пикселям** (`image_signature`) только группы с одинаковыми
  размерами. Два фото совпадают, когда их пиксели идентичны, независимо от
  различий в байтах.
- **Видео → точно по байтам**, через «воронку» размер → быстрый хеш (64 КБ) →
  полный SHA-256, чтобы уникальные видео никогда не читались целиком.

Группы сортируются по освобождаемому месту (сначала самые крупные, суммируется по
фактическому размеру каждого дубликата). Работает асинхронно, с логом прогресса и
кнопкой Cancel.

### Оставленный файл и пометка

В каждой группе **самый старый** файл (наименьшее `st_birthtime`/`st_mtime`)
остаётся нетронутым; остальные копии помечаются. Используется **префикс** `DUP_`
(`naming.flagged_name`), а не вставка в середину имени, потому что Finder/Проводник
обрезают длинные имена посередине (`начало…конец.ext`), из-за чего вставка в
середину была бы не видна — а префикс всегда виден. Файлы, уже начинающиеся с
`DUP_`, и всё, что уже лежит в папке `DUP/`, пропускаются, поэтому оба действия
идемпотентны; при совпадении имён добавляется `_1`, `_2`…

### Отчёт

`ReportWriter` сохраняет `_DUPLICATES_REPORT_<дата>_<время>.md` во входной папке:
шапка со сводкой (просканировано файлов, групп, лишних копий, освобождаемое место)
и по одному разделу на группу со списком оставленного файла и путей всех
дубликатов. Экранный лог повторяет это, но ограничен первыми 100 группами (отчёт
всегда содержит все).

### Ключевые компоненты

| Компонент           | Ответственность                                                               |
| ------------------- | ----------------------------------------------------------------------------- |
| `DuplicateScanner`  | фото по пикселям, видео по «воронке» байтов → `DuplicateGroup[]`.             |
| `DuplicateGroup`    | Набор с идентичным содержимым: оставленный + дубликаты; освобождаемый размер. |
| `ReportWriter`      | Формирует отчёт в Markdown.                                                   |
| `naming`            | Префикс `DUP_`, имя папки `DUP/`, детекция уже помеченных.                    |
| `DuplicatesService` | Скан (только чтение), пометка на месте и перенос в `DUP/` (всё явно).         |
| `DuplicatesTab`     | Интерфейс Flet: папка, Scan / Move / Rename / Undo / Cancel, лог.             |

## Обзор интерфейса

- **Шапка** (`app_header.py`) — название и подзаголовок приложения.
- **Вкладки** (`app_tabs.py`):
  - *Photo Recovery* — рабочая функция.
  - *Photo & Video Renamer* — рабочая функция (переименование + раскладка по дате, Undo).
  - *Duplicates Finder* — рабочая функция (скан → отчёт → пометка, Undo).
- **Вкладка восстановления** (`recovery_tab.py`) — три карточки папок (ORIGINAL /
  RECOVERED / OUTPUT), переключатель перемещение/копирование, кнопки Process/Cancel
  и лог только для чтения.
- **Вкладка переименования** (`renamer_tab.py`) — одна карточка папки INPUT,
  выпадающий список пресетов + поле шаблона + живой предпросмотр, кнопки
  Rename/Undo/Cancel над логом.
- **Вкладка дубликатов** (`duplicates_tab.py`) — одна карточка папки INPUT и кнопки
  Scan / Move to DUP folder / Rename in place / Undo / Cancel над большим логом
  (остальное — в отчёте).

  который открывает системный диалог выбора папки Tkinter (по умолчанию
  `~/Downloads`) и возвращает выбранный путь через stdout. Запуск в отдельном
  процессе нужен, чтобы не смешивать событийные циклы Tkinter и Flet.

## Замечания по безопасности

- `DuplicateProcessor` по умолчанию работает в режиме **копирования**.
  Переключатель **«Move files instead of copying»** на вкладке Photo Recovery
  меняет режим на перемещение; значение передаётся по цепочке интерфейс →
  `PhotoRecoveryService` → `DuplicateProcessor`. Переключатель **выключен** по
  умолчанию (безопасное копирование), а активный режим печатается в лог в начале
  каждого прогона. В режиме копирования исходные папки не изменяются.
- Классификация — **по содержимому** (для фото по пикселям, для видео по SHA-256):
  нет ложных «дубликатов» из-за совпадения имён, а полное сравнение содержимого
  на практике исключает риск коллизий.
- **Renamer перемещает файлы на месте** (по своей природе это изменение). Его
  страховка — кнопка **Undo**, отменяющая самый последний прогон. Undo хранится в
  памяти и действует в рамках сессии — теряется, как только вы запускаете новое
  переименование или закрываете приложение.
- **Duplicates Finder никогда не удаляет** файлы. Сканирование — только чтение;
  пометка лишь переименовывает или переносит лишние копии как отдельный явный шаг
  и обратима через Undo (та же оговорка про сессию). Что действительно удалить —
  решаете вы вручную, изучив отчёт.
- Геокодинг — **офлайн** (`reverse-geocode`); GPS-координаты не покидают компьютер.
